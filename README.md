# المساعد المؤسسي الذكي

وكيل ذكي يجيب عن أسئلة الموظفين من مستندات الشركة وقواعد بياناتها، وينفّذ طلبات الإجازة — مع ذكر المصدر وإظهار الأدوات المستخدمة في كل إجابة.

![واجهة المساعد](docs/screenshot.png)

---

## المشكلة

المعرفة المؤسسية موزّعة بين نوعين مختلفين من المصادر:

- **مستندات نصية** — سياسات، لوائح، إجراءات
- **بيانات مهيكلة** — أنظمة الموارد البشرية، جداول الموظفين

البحث بالكلمات المفتاحية يفشل حين تختلف صياغة السؤال عن نص المستند. والنماذج اللغوية العامة لا تعرف بيانات الشركة، وقد تخترع إجابات تبدو موثوقة.

## الحل

وكيل يختار الأداة المناسبة لكل سؤال:

| نوع السؤال | الأداة | مثال |
|---|---|---|
| سياسات وإجراءات | بحث هجين في المستندات | "ما شروط العمل عن بعد؟" |
| بيانات موظف | استعلام SQL | "كم رصيد إجازة فلان؟" |
| إجماليات ومقارنات | تجميع على كامل البيانات | "كم إجمالي البدلات؟" |
| تنفيذ عملية | معاينة ثم تأكيد ثم كتابة | "أبي إجازة 5 أيام" |

## المعمارية

```
مستخدم
  ↓
واجهة (HTML مخصّصة داخل Streamlit)
  ↓  HTTP
خادم FastAPI
  ↓
طبقة الحماية — فحص المدخلات ومعاملات الأدوات
  ↓
الوكيل — يختار الأداة ويخطّط
  ├── بحث هجين      → ChromaDB + BM25
  ├── استعلام بيانات → SQLite
  ├── أدوات حساب
  └── تنفيذ عمليات   → معاينة ← تأكيد ← كتابة
  ↓
حارس التنفيذ — يمنع ادّعاء عمليات لم تحدث
  ↓
النموذج اللغوي
```

الفصل بين الطبقات يسمح باستبدال الواجهة (جوال، Teams) دون تعديل المنطق. توجد واجهتان في المشروع تستهلكان نفس الخدمة.

## التقنيات

| المكوّن | التقنية | سبب الاختيار |
|---|---|---|
| الخادم | FastAPI | توثيق تفاعلي مولَّد من الكود، تحقّق تلقائي بـ Pydantic |
| الواجهة | HTML مخصّص داخل Streamlit | تحكّم كامل في الشكل مع بساطة التشغيل |
| النموذج اللغوي | Groq (gpt-oss-120b) | واجهة متوافقة مع OpenAI — تبديل المزوّد بسطرين |
| Embeddings | multilingual-e5-base | نموذج retrieval، يعمل محلياً فلا تغادر المستندات الشبكة |
| قاعدة المتجهات | ChromaDB | تخزين دائم مع metadata وفلترة مدمجة |
| بحث الكلمات | rank_bm25 | يمسك الأسماء والمعرّفات التي يفوتها البحث الدلالي |
| البيانات المهيكلة | SQLite | استعلامات دقيقة بلا خادم؛ المسار لـ PostgreSQL مباشر |
| المستندات | PyMuPDF · python-docx · openpyxl | PDF و Word و Excel |
| الاختبارات | pytest | 139 اختباراً |

## الميزات

**المستندات**
- رفع PDF و Word و Excel ومعالجتها تلقائياً
- تقسيم Word حسب العناوين، و Excel صفاً صفاً
- قراءة نتائج معادلات Excel لا نصها
- منع تكرار المستندات ببصمة المحتوى
- استشهاد بالملف والقسم لكل إجابة

**الوكيل**
- تسع أدوات، يختار بينها حسب السؤال
- بحث هجين: دلالي + كلمات مفتاحية مدموجان بـ RRF
- ذاكرة محادثة — يفهم "طيب كم السنوية حقته"
- إظهار الأدوات المستخدمة في كل رد

**الأتمتة**
- تسجيل طلبات الإجازة بعد معاينة وتأكيد صريح
- عرض الطلبات وإلغاؤها
- حجز الرصيد للطلبات المعلّقة
- فحص ملكية — لا يلغي موظف طلب موظف آخر

**الحماية**
- رفض محاولات prompt injection
- رفض الطلبات واسعة النطاق
- تنظيف نص المستندات من تعليمات مدسوسة
- فحص معاملات الأدوات قبل تنفيذها
- **حارس ضد ادّعاء تنفيذ لم يحدث**

**القياس**
- لوحة إحصاءات: عدد الأسئلة، نسبة الإجابة، الأزمنة، الرموز المستهلكة
- توزيع استخدام الأدوات
- تسجيل كل عملية كتابة بمستوى تحذير للتدقيق

**الواجهة**
- تصميم عربي كامل (RTL)
- وضع فاتح وداكن
- تاريخ محادثات، تصدير Markdown، نسخ، إعادة توليد
- بحث في المستندات المرفوعة

## التشغيل

```bash
git clone https://github.com/rakan1333/enterprise-ai-assistant.git
cd enterprise-ai-assistant

pip install -r requirements.txt

cp .env.example .env
# ضع مفتاح Groq في .env

python build_db.py          # قاعدة بيانات تجريبية
```

نافذتان منفصلتان:

```bash
uvicorn api:app --reload    # الخادم
streamlit run ui_app.py     # الواجهة
```

التوثيق التفاعلي: `http://localhost:8000/docs`

## مشكلات واجهتني وكيف حللتها

هذا القسم أطول من قسم الميزات عمداً — الميزات يبنيها أي أحد، والتشخيص لا.

### 1. إجابة خاطئة تبدو موثوقة

سؤال عن إجمالي البدلات أعطى **51,200** بدل **72,000**. النظام استرجع 3 أقسام من 5، جمعها بدقة، وذكر مصادر صحيحة — فبدت الإجابة سليمة تماماً.

**التشخيص:** ليست هلوسة. `top_k` ثابت يقتطع السياق، والنموذج لا يملك وسيلة ليعرف أن ما رآه ناقص.

**الحل:** توجيه أسئلة التجميع لأداة SQL عبر الوكيل. RAG أداة استرجاع لا أداة تجميع.

### 2. البحث الدلالي لا يجد الأشخاص

سؤال عن رصيد موظف بالاسم لم يسترجع سجله إطلاقاً.

**التشخيص:** نماذج embedding تمثّل المعنى، والأسماء بلا معنى دلالي. "خالد الدوسري" و"أحمد الشمري" متجاوران في فضاء المتجهات لأن كليهما "اسم شخص".

**الحل:** أداة استعلام مباشر، ثم بحث هجين يضيف BM25 للمطابقة الحرفية.

### 3. الاسترجاع يفشل رغم وجود الإجابة

**المسار الخاطئ:** جرّبت رفع العتبة، ثم `top_k`، ثم تعديل الـ prompt. كل حل حسّن قليلاً ولم يُصلح شيئاً.

**التشخيص:** طباعة **كل** القطع مرتّبة كشفت أن مدى المسافات لـ 19 قطعة كان 0.173 فقط، والإجابة الصحيحة في المركز الثامن خلف صفوف بيانات غير ذات صلة. النموذج لا يفصل بين النصوص أصلاً.

**السبب الجذري:** `paraphrase-multilingual-MiniLM` نموذج مُحسَّن للترجمة، استُخدم للبحث.

**الحل:** التحول لـ `multilingual-e5-base`. قفزت الإجابة للمركز الأول، وتحولت فجوة المعايرة من **−0.121** إلى **+0.058**.

**الدرس:** حين تتراكم الحلول الجزئية دون أن تحل شيئاً، المشكلة طبقة أعمق. قِس المكوّن نفسه لا معاملاته.

### 4. الاستشهاد بمصدر خاطئ

النموذج نسب معلومة للمصدر الأول وهي في الثاني.

**التشخيص:** كل قطع Word كانت تحمل الموقع نفسه ("المستند")، فلا يملك النموذج ما يميّزها.

**الحل:** تقسيم Word حسب العناوين. الاستشهاد الخاطئ أخطر من غيابه لأنه يمنح ثقة زائفة.

### 5. الحماية تُتجاوَز عبر الذاكرة

بعد إضافة ذاكرة المحادثة، اكتُشف أن سؤالاً **حجبته الحماية** كان يُحفظ في التاريخ ويُرسل كسياق في الدورة التالية — فيراه النموذج وينفّذه.

**الحل:** الذاكرة تحمل الأزواج المكتملة فقط. سؤال بلا إجابة مشروعة لا يُعاد إرساله.

**الدرس:** كل ميزة جديدة تعيد فتح أسئلة الأمان. لا يكفي أن تكون الحماية صحيحة عند بنائها — يجب أن تبقى صحيحة.

### 6. تجاوز الرصيد بطلبات متعددة

الطلبات المعلّقة لم تكن تُخصم من الرصيد، فأمكن تقديم طلبين مجموعهما يتجاوزه.

**التشخيص:** ثغرة **منطق عمل** لا خطأ برمجي. الكود يعمل بلا استثناء، لكن القاعدة التجارية ناقصة.

**الحل:** الرصيد المتاح = الرصيد − المستخدم − المعلّق.

**الدرس:** الاختبارات تحمي من كسر الكود، لا من قواعد عمل ناقصة. تُكتشف بمراجعة من يعرف المجال.

### 7. ادّعاء تنفيذ لم يحدث

الوكيل كتب **"تم الإلغاء بنجاح"** دون استدعاء أي أداة. التحقق من قاعدة البيانات أظهر أن الطلب لا يزال قائماً.

**التصنيف:** هلوسة تنفيذ (phantom action). أخطر من هلوسة المعلومة لأن المستخدم لا يستطيع اكتشافها بالقراءة — سيصدّق أن العملية تمّت.

**السبب:** الـ prompt منع اختراع الحقائق ولم يمنع ادّعاء الأفعال. والنموذج يفرّق بينهما.

**الحل:** طبقة `action_guard` تقارن ادّعاء الرد بسجل الاستدعاءات الفعلي. إن ادّعى الرد تنفيذاً ولم تُستدعَ أداة كتابة، يُستبدل الرد.

**الدرس:** الحماية بنيوية لا سلوكية. النموذج لا يستطيع خداع مقارنة لا تسأله.

## قرارات هندسية

**لماذا embeddings محلية؟** سياسات حماية البيانات في القطاعات المنظّمة تمنع إرسال المستندات لخدمات خارجية.

**لماذا أداتان للإجازة بدل واحدة؟** `preview` لا تملك كوداً يكتب — فلا يمكنها الكتابة حتى لو أراد النموذج. **اجعل العملية الخطرة مستحيلة، لا مجرد ممنوعة.**

**لماذا يعيد `submit` التحقق كاملاً؟** لأنه قد يُستدعى مباشرة متجاوزاً المعاينة. لا نثق بأن الخطوة السابقة تمّت.

**لماذا الإلغاء ثم الإنشاء بدل التعديل؟** سجل التدقيق يبقى كاملاً — الطلب القديم `cancelled` والجديد `pending`. في أنظمة الموارد البشرية التاريخ لا يُمحى.

**لماذا RRF بلا أوزان؟** لأن الأوزان تتطلب معايرة، والمقاييس غير قابلة للجمع أصلاً (مسافة 0.14 مقابل درجة 7.3). RRF يستخدم الترتيب فقط.

**كيف نُقلّل الهلوسة؟** أربع طبقات: عتبة تشابه، prompt يمنح مخرجاً للاعتراف بالجهل، temperature صفر، وحارس تنفيذ برمجي.

## قيود معروفة

- **لا توجد مصادقة** — كل مستخدم يرى كل شيء ويحذف أي مستند. أكبر ثغرة حالياً.
- ملفات PDF الممسوحة ضوئياً تحتاج OCR
- لا توجد أدوات للترتيب أو المتوسطات ("من أعلى رصيد؟" يفشل)
- الوكيل بلا حالة معلّقة — قد لا يربط "نعم" المجرّدة بخطة وصفها في الرد السابق
- `build_db.py` تدميري — يحذف القاعدة ويعيد بناءها. الإنتاج يحتاج هجرات
- المعالجة متزامنة — الملفات الكبيرة تحجب الطلب
- SQLite مناسب للتطوير؛ الإنتاج يحتاج PostgreSQL
- تسطيح جداول Excel إلى نص يفقد بعض البنية
